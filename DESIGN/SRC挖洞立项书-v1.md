# SRC 挖洞立项书 v1（行营五槽 · 商业化全流程项目）

> 2026-09-24 用户定盘。v1 为讨论基线：目标/约束已定，验收与假设逐条待验证；架构细节后续迭代。
> 前置分析：tsecbench 榜首三局 + 开源 agent 榜单前 10 拆解 + StrikeAgent 源码 + 20935/21611 会话取证（均见 RECON/）。

## 一、目标（字典序）

1. **收益优先**：收益 = SRC 赏金 + 产品出售（agent/流程可直接卖；组装开源组件合法合规即可，不必全自研）。
2. **练硬功夫，捏软柿子**：agent 必须有攻坚克难能力（硬功夫）；目标选择上专挑"名下资产烂代码多 + 政策原因不得不赔付"的 SRC（软柿子）。
3. **全流程**：资产发现 → 目标评分 → 挖洞（公开漏洞 + 自研代码漏洞 + 业务逻辑漏洞）→ 验证 → 报告生成 → 平台上传，除注册/登录等少量人工配合外全部自动化。

## 二、约束（硬软分开）

**硬约束**：
1. 绝大多数 SRC 是黑盒 web——**白盒 SAST 主体不用**，但保留"黑盒可达的半白盒"：前端 JS bundle 分析、泄露的源码/仓库/备份文件、移动端反编译（自研代码漏洞在黑盒下的现实入口）；
2. 全程合法合规：授权内行动、留证、不越权、不用盗版/违规工具、先报告后公开；
3. **IP 有限且不能封**——但注意双层节奏（用户裁定）：**单目标侧必须低慢小**（每目标 ≤ 个位数 req/s、WAF 退避），**我方侧全网并行**（同时打 1000 家企业/10000 资产，全局吞吐可达万级 req/s）——约束③的本质是**每目标限速 × 全网并行**的调度问题，不是全局降速；
4. 验证阶段服务器暂不升级（当前机器够用）。

**软约束**：人工可配合（注册/登录/验证码/个别验证动作）；工具与模型可采购；模型/搜索无限制。

## 三、验收口径（done 定义 + 停止条件）

- **验证阶段 done**：选 1-2 个真实 SRC 平台、≥5 个目标，全流程跑通（资产→评分→洞→PoC→报告→上传），产出 ≥1 份有效漏洞报告（平台确认/赏金入账）；产品原型可演示（同一引擎多平台配置化）。
- **停止条件**：连续 3 个目标周期（暂定每周期 2 周）零有效报告 → 停挖，复盘转向产品化；IP 被封 ≥2 次未破 → 停，先修执行层节奏。
- **非目标**：不追求 CTF 刷榜速度；不接未授权委托；不碰内网渗透/APT 交付。

## 四、规则域（红线）

- 只打 SRC 明确授权的资产范围（SRC 规则域 + 平台 scope 双确认）；
- 每一步攻击动作与授权上下文同落盘（合规留证 = 法律盾 + 报告素材）；
- 发现即报告：不脱库、不拖数据、不破坏业务、不做持续性后门；
- 报告如实：误报宁可少报，不上夸大影响面（T3MP3ST 证据门标准）。

## 五、架构决策（已定）

1. **沿用神策调度内核**（题队列/优先级/状态门/收兵/全旗告警均迁移），其余无现成成品可组装。
2. **LLM 为核心（用户倾向确认）**：计划层单主脑（= 御主）；"角色"只在工具集确实不同时存在（侦察/利用/验证/报告四套工具集），不做人设剧场；**状态出脑**（攻击图 + shells/creds/findings 文件 + 开工必读）。
3. **工具清单（10-15 个，不带 150）**：
   ①浏览器级 HTTP（渲染/交互/人工登录态）②代理截流（认证流量参数挖掘）③扫描器子进程（nuclei/ffuf/sqlmap 带词表/时间盒/每目标限速罩）④JS/接口提取（bundle→API→参数）⑤指纹与组件版本 ⑥资产发现（被动源为主：证书透明/公开快照，省 IP）⑦状态图+负结果文件 ⑧验证执行器（proof-by-exploitation + 复测）⑨报告生成器（SRC 模板）⑩请求预算器（全局吞吐 × per-host 限速 × 封禁退避）⑪WAF 绕过知识注入 ⑫业务逻辑差分工具（双账号/多角色对比，用人工配合）。
4. **可信发现管线**（四合一）：证据门（无真实输出不标 verified）+ 逐字证据回执 + proof-by-exploitation + 双流对账去重 + 二次验证。
5. **目标评分模块**（商业核心，所有开源项目都没有）：烂代码信号（历史漏洞密度/框架版本/公开组件/泄露面）× 赔付意愿信号（强监管行业/历史赔付案例/赏金记录）→ 输出"今天打谁"。
6. **双层节奏调度**（用户裁定，v8.6 调度内核的 SRC 变体）：全局调度多目标扇出（万级吞吐）× 单目标严格限速（低慢小）——现神策的槽位/优先级/排满义务迁移为"多目标并行排满"，时间盒迁移为"每目标请求预算"。
7. **产品化边界**：核心引擎（调度/状态/验证/报告）是产品；逐平台适配（字段/模板/限速参数）放配置与知识库。
8. **可参考项目**（已拆解）：CyberStrikeAI（黑板+交接包+认证重放）、T3MP3ST（证据门/围栏/dry_run）、shannon（proof-by-exploitation+对账）、PentestGPT（逐字回执状态机）、cai（杀伤链分组+复测去误报）、Nettacker（YAML 模块+历史漂移作已知 CVE 子模块）；HexStrike 无价值。

## 六、假设日志（待验证）

1. 目标评分能显著提升投入产出比（烂代码 × 赔付意愿双信号有效）；
2. "单目标低慢小 × 全网并行"能同时满足 IP 约束与收益效率（封禁率可接受）；
3. 半白盒路径（JS/泄露文件/移动端）是黑盒 SRC 发现自研漏洞的主要现实入口；
4. 业务逻辑漏洞可通过双账号差分 + 状态机走查 + 参数挖掘发现（能力 2 的可行性）；
5. LLM 核心 + 工具集分层 + 状态出脑，优于角色扮演式多 agent（效率与质量）；
6. 现成开源组件（扫描器/MCP/浏览器自动化）组装成本 < 自研，且不损产品可售性；
7. 全流程自动化闭环在人工只做注册/登录的配合下可达（验收口径的可行性）。

## 七、未决事项（下轮讨论）

- 目标评分的数据源与权重；首个验证 SRC 平台选择；
- "攻坚持续性"与"捏软柿子"的兵力配比（多少资源留给硬骨头）；
- 产品形态（SaaS/私有化/按报告分成）与合规售卖边界；
- 报告-上传适配层先支持哪些平台（漏洞盒子/补天/众测/海外 H1/BC）。
