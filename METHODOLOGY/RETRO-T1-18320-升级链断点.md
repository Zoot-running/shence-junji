# 复盘:Tsecbench v1 首战(run 18320)——升级链为什么全程没有触发

> 2026-09-15。结果:82.3 分(18470/23000, 80.3%),打满 6h 钟;榜一门槛 Cairn_Y 97.14,未上榜一。
> 本复盘聚焦用户核心问题:**升级(二次征集/换视角)为什么一次都没发生**。

## 一、战局全貌

- 开局极快:40min 43%、70min 68.7%(v2 纪律 + 种子迁移修复后,比 18293 同帧的 3.5% 快一个数量级);
- 之后撞上 **b-02(hard 1800 分、6-flag 多阶段 web 题)的硬墙**:74% 处磨了 ~3 小时;
- 收尾钟前破出 +1410 分,80.3% 收官;最后 2 分钟的 status:campaign done=62 failed=16 blocked=75,
  尚有 ~10 题(f2-01..f2-08 等)"solving"未终态。

## 二、升级链的三层断点(为什么没升级)

设计(JISI-V2-DESIGN 第 3 层)的升级路径有两条:①死思路 ≥50% → ⚠️ → xiaochang_refanout;
②末段(≤60min)hard 未破 → ⏰ flag → refanout 全模型档。实测两条都没走通,断点如下:

### 断点 1(归因层):主 agent 全程 0 次判死
- xiaochang_report 去重后 **369 次,全部 verdict=complete;failed=0、skipped=0**;
- 没判死 → `why` 无从填起(全 run 0 条 why)→ 归因四分类一次都没被使用;
- 深层原因:判死纪律("征集穷尽+兵力≥3")没有给出任何"该判死"的信号,agent 的
  goal 循环只会无限重派——**"不判死"是 agent 面对无信号时的默认行为,而非例外**。

### 断点 2(信号层):⚠️ 升级建议的计数源被断点 1 饿死
- ⚠️ 触发条件 = 死思路/采纳 ≥50%,而"死思路"只在
  `settleAdoptions(code, win=false, attribution=approach-dead-end)` 时计数;
- 该调用发生在 xiaochang_report 带 why=approach-dead-end 的终局——断点 1 使其恒 0;
- 结果:死思路恒 0 → 升级建议永不出现(全 run 0 次)。

### 断点 3(机制层,实锤 bug):末段逃生门从未进沙箱
- 末段 flag(≤60min + hard 未破)是**唯一不依赖 why** 的升级触发——设计上的逃生门;
- 实锤:末段 flag 的代码引入时带着**重复声明 `const remaining`**,esbuild 报
  "The symbol remaining has already been declared" 构建失败;
- 更糟的是构建命令走了 `npx esbuild ... | tail -1`——**管道吞掉了 esbuild 的失败退出码**,
  shell 看到 tail 的 0,流程继续,提交并同步的是**旧 lib**;
- 沙箱里的 runner 自始至终没有末段 flag 代码(grep 产物 0 命中)。
- 已修:移除重复声明+死代码;构建改用 `npm run build` 直跑并**验证产物含标志**
  (hardOpen/kimi-k3/pro 已确认在 lib 中)。

### 断点 4(执行层):agent 即使看到信号也未必升级
- 末段 60min 窗口内,agent 在磨 b-02 的 flash 路线(racing/coordination 消息为证),
  refanout 全 run 0 次;
- 设计第 3 层写的是"默认动作可改判",实际实现是"只打提示等 agent 执行"——
  纪律没有被机制默认化,这是设计-实现间的落差。

## 三、升级链断点小结(一张图)

```
设计链: report(failed,why) ──▶ deadIdeas 计数 ──▶ ⚠️ 升级建议 ──▶ refanout
                                    ▲                    │
断点1: 0 判死 ────────────────────────┘                    │
断点3: 末段逃生门(不依赖 why)未进沙箱 ──────────────────────┘
断点4: 就算有建议, 执行靠 agent 自觉
```

## 四、v2 机制的正面对照(机制本身在跑的证明)

- jisi_pick 537 次、jisi_adjudicate 693 次——裁决/契合度大规模使用;
- Thompson 探索:pro 首场大考 1357 调用、9 模型目录全被 pick 过(冷启动死循环破除);
- 种子迁移修复生效(model_report:flash 0.98 n=64 / glm 0.90 n=19);
- 花费(谷价口径):flash ≈¥36 + pro ≈¥38 + kimi/glm ≈¥15 ≈ ¥90 经济账。

## 五、修正计划(分析定案后按流程走:本地验证→上仓库→托管打包才碰容器)

1. **信号源去依赖**(修断点 2):⚠️ 升级建议的"死思路"改用**该题终态失败次数**(hufu ledger
   里 failed 终态的直接计数,不依赖 why 字段);
2. **末段默认动作**(修断点 4):末段 flag 出现时,status 返回里附**一键 refanout 的具体调用**
   (code+models 全拼好),或 runner 直接机制触发 refanout(agent 可改判);
3. **"该判死"信号**(修断点 1):status 增加"该题已磨 N 分钟/连续失败 M 次无终态"提示,
   给 agent 判死的客观依据;
4. **多 flag 题拆工作项**:b-02(6 flags)按 flag 粒度拆 hufu item——派单/账本/难度都按 flag,
   满分口径对齐;
5. **构建纪律**:所有 esbuild 构建用 `npm run build` 直跑(无管道),并在本地验证脚本里
   断言产物含关键标志——"构建静默失败"此类事故不再可能。
