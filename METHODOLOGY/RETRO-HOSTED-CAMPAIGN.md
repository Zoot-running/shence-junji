## 三、根因(修正认知)

1. **8C16G 单沙箱 = 并发天花板**。本地局 20+ 执行者把 40 题全量并行磨掉,
   硬题互相掩护(难题在跑的同时简单题批量收割);托管局执行者并发低
   (峰值 ~21 会话,但有效并行更低),硬题只能排队逐个磨——g-25 从 10 分钟
   变 225 分钟就是排队+轮换损耗的累积。
2. **平台双瓶颈在托管下被放大**:3 容器上限 + "提交必须容器在线"= 全局串行点。
   本地大并发能把"已解待交"的 flag 排成厚队列快速冲刷;托管求解慢,队列薄,
   串行点变成主循环。
3. **工具已不是瓶颈(v9 证伪了此前的判断)**:fanout/GLM/思考档位全部修好并
   实战生效,v9 开局速度反超本地——但工具修好并没有把硬题层提速。
4. **行为级根因(用户追问后实测)**:托管主 agent 用 bash sleep 当等待器,
   **睡掉 293/319 分钟(92% 墙钟)**;LLM 吞吐 5.3 calls/min(vs 本地 70.2,
   同沙箱 Cairn 30.6)。机制上 settle 通知可直达主会话(fanout notify 已实证),
   但虎符一次性执行者走静默落账,主 agent 只能轮询;叠加开战令"稳健第一"的
   防守语调,agent 把第三目标(省钱)优化成了第一目标——**"8C16G 天花板"的
   早前表述不成立,Cairn 同沙箱 729 会话即证**。
5. 修正:3 容器+提交在线是本地托管同款规则,不是托管特有串行点(本地同样规则
   43 分钟满分)。
4. 停表损耗:三局都没有把平台钟用满(v7 提前 3.5h、v9 提前 41min、v10 手动停),
   叠加预算/条款措辞问题——但即使补满,按 v9 的硬题速率也到不了满分。

## 四、下一步(按收益排序)

1. **调度形态改造(治本)**:学榜一 Cairn 的架构——729 个**短会话**(~10.6
   调用/会话)= 细粒度小任务并行,而不是我们"一题一个长会话执行者"。
   硬题开局即拆成多路细粒度并行派单,执行者会话瘦身(低 effort 起步、
   小上下文),让 8C16G 上跑出更高有效并发。
2. **g-02/g-24 攻法本地复盘**:g-24 托管局被 fanout 带进死空间后误判"无解"
   (run 11 用单密钥 fake_admin 路线解出);g-02 连续三局未破。本地把这两题
   的确定性解法复盘透(不违反 clean-room——是我们的攻法沉淀,托管局仍从零,
   但 fanout prompt 能喂更高质量的"失败事实")。
3. **publish 决策**:v7 局 39/40(96.63%)若 publish = 榜二;满分榜一仍差一局。
   用户已定调:满分才 publish。
4. 停表条款 v10 已修(budget 360 + 唯一依据=平台钟/满分)——下局不再重复此错。

## 五、四栏复盘(整场托管战役)

- **预期 vs 实际**:预期工具修复后恢复本地水平;实际 v9 开局超本地、硬题层
  5-22× 慢、终局 36/40。工具假设被证伪,资源/形态假设被证实。
- **决策-结果**:D1 试跑六局逐个排障(每局 3-5 分钟定位)→ 全部根因确凿 ✅;
  D2 打包审计拦下密钥+私知两枚真雷 ✅;D3 v9 全修复上正式局 → 成绩未升
  ⚠️(决策正确,预期模型错误);D4 验证轮先于正式局 → 避免带病上场 ✅。
- **根因**:见 §三;另记 platform 侧零故障(全程无一次误判平台)。
- **教训分类**:
  - A 通用方法论:"工具修复≠能力恢复——先验证瓶颈假设,再投入修复";
    "细粒度短会话并行(榜一实证)优先于长会话执行者";
  - B 机制先验:submit 需容器在线/容器地址复用/hint 负收益/空置回收(已入档);
  - C 一次性事实:三局时间线/逐题倍率(本文档);
  - D 平台缺陷:无。
