# 计划评审协议（PLAN-REVIEW）

> 方法论 POC W2 交付物之一。适用：主 agent 派活前的**计划自审**、战后**人工回审**、以及（POC 通过后）runner/watch 的**机制校验**。CTF 先行，泛化后议。

## 一、计划必须包含的六要素（缺一即重写）

1. **依赖图（DAG）**：任务拆解后标明依赖——无依赖的即可并行；图是并行的载体，没有图就没有并行依据。
2. **关键路径**：最长串行链 = 用时下限；把它标出来，看它是否可再拆（拆串行链才是真提速）。
3. **并行扇出与汇聚点**：每条并行分支必须写明**谁在何时做综合/消歧**（fanout 120 份报告无汇聚 = 灾难）；汇聚点也是质量闸。
4. **资源上限与证明**：并发上限/配额/预算显式列出，并证明计划不超限；宽度免费处开满宽度（如思路征集），受限处把预算给最高价值路径（如 3 容器）。
5. **执行者分工**：计划者 vs 执行者边界——主 agent 排计划/调度/验收，不下场解题（唯一例外：执行者已交 FLAG_CANDIDATE 的临门一脚，≤3 个工具调用）。
6. **验收与停止条件**：每个任务的 done 定义 + 失败判定；全计划的总验收口径与停止条件（"什么时候算失败"与"什么时候算成功"一起定义）。

## 二、自审清单（主 agent 派活前过一遍，逐条问自己）

1. 有没有依赖图？没有 → 先画。
2. 有没有"可以并行却被我排成串行"的？有 → 改并行（run 6/8 实证：串行亲挖是最贵的一类）。
3. 每条并行分支有没有汇聚点？没有 → 补。
4. 资源上限写了吗？计划会不会超？超 → 重排优先级。
5. 哪一条我要亲自做？理由是什么？（除临门一脚外都应派执行者）
6. 每个任务的验收口径写了吗？

## 三、评审时机

- **派活前**：主 agent 自审一次（六要素+清单）；
- **目标变更后**：按变更条款**基于当前已完成工作重新排计划**，新计划再过一遍自审；
- **战后**：人工回审"计划 vs 实际执行"对照表（见 RETRO-CLASSIFICATION 第 1 栏）。

## 四、机制校验（POC 通过后机制化，现阶段靠 SKILL 纪律）

- runner/watch 检查 `plan-<runId>.md` 存在且含六要素标题；缺失 → 明确提示主 agent 补写（只告警不代决策）。
- 与校场现有 F19 空闲告警同构：机制兜底纪律，不替代 agent 判断。

## 五、反模式清单（实战实证）

- 串行亲挖（run 8：20 题主 agent 亲解 = 2 小时串行墙钟）；
- 无汇聚的并行（报告洪水淹死调度）；
- 无上限的扇出（并行度超出资源/合并能力）；
- 计划不含停止条件（"做完"与"失败"都没定义 → 提前收官或空烧）；
- 计划与资源账脱节（排了并行却不算 token/槽位预算）。
