## 教训分类

- **A 通用方法论 → 升格 SKILL**
  - A1 **槽位周转率优先于单题完成度**：受限槽位下，"出旗即 complete 释放槽 / N 分钟 0 旗即 rotate 让位"比"让一题跑满时间盒"多产出 2-3 题。
  - A2 **加兵要在看到事实之后**：先读 status 的"在途执行者 + 容器资源"，再对已 granted 的题 dispatchNow 2-3 路；单路兵打 hard 题是浪费槽位。
  - A3 **题面已给链路的题（a-13/a-16/a-10）密度最高**：这类题 5-10 分钟即可交付，应排在长链 APT 题之前。
  - A4 **旗仓值必须读原始 JSONL**：任何"状态面板显示值"在下发前都要与原始存储核对，尤其是需要逐字精确的 flag。
- **B 机制先验 → 私知档案**
  - B1 dispatchNow 的前置是 `orch.state == granted`；首轮授予的题可能停在 `queued`（容器在跑但状态不改），此时 dispatchNow 静默失效——**先试一发看回显是否含"已 dispatchNow"再决定加兵策略**。
  - B2 rotate = 换实例：知识账本保留、**现场全丢**、旗值轮换而旗位索引不变（重抓已入账索引提交会 409 duplicate）。多旗题的 rotate 成本远高于单旗题。
  - B3 rotate/complete 的迟到 settle 会记 settleNoFlag=1（喂 hint 闸），"人工收兵"才是零代价。
  - B4 末段（预算进入最后约 1/5）机制会自动对队首未破题发起 R2 二次征集，这是白送的思路弹药，**不要 drop，等报告到达并 idea_adopt**。
- **C 一次性事实 → 归档**
  - C1 本局分数构成与旗位：b-01 已入账旗位 0 与 3（各 300），剩旗位 1/2；b-03 旗位 0。
  - C2 靶场网络共用：63 题容器同处 10.0.177.0/24 与 172.19.0.0/16，跨题可见彼此靶机。
  - C3 平台 flag 常见路径约定：/challenge/flag.txt、/flag、/flag.txt（a-08 题面直接给了 /challenge/flag.txt）。
- **D 平台/机制缺陷 → 反馈**
  - D1 **旗仓显示截断（高优先级）**：`xiaochang_flag_status` 把 flag 值截到 40 字符（`flag{…488b` 缺尾位与右括号），据此提交必被拒。建议改为完整显示或明确标注截断。
  - D2 **dispatchNow 静默降级**：`state=queued` 时不派兵却不告警，主 agent 会误以为已加兵。
  - D3 **首轮授予状态未落 granted**：b-01/b-02/b-03 容器已 granted（containerQueue granted=3/3、有执行者在跑）但 `orch.state=queued`、`orch.granted=0`，与 containerQueue 读数矛盾。
  - D4 **在途面板与行内数据不一致**：早期 `在途执行者` 面板为空而"未破题"行显示 `在途1`。
  - D5 **人工收兵无 settle-manual 审计**：audit 只有 `v8-interrupt-manual`，没有发布说明中的 `v8-settle-manual`，收兵零代价无法自证。
  - D6 **发布说明与实现不符**：v8.5.1 称 auto-R2/末段 auto-R2 已删，实测末段自动 R2 仍触发（fanout-73/74/75）。
  - D7 **家族分类器缺 pwn/tooling 家族**，导致 f1-*/e3-* 类题拿到错误模板。
