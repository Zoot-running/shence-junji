# 立项书：神策方法论 POC（项目化 + 并行计划 + PDCA 复盘）

> 这是"项目化方法论"的第一个应用对象——拿它自己开刀（2026-09-11，主调度草拟，待用户审定）。
> 本文件同时是**立项书模板的实例**：五个槽位（目标/约束/验收/规则域/假设）就是模板本体。

## 0. 缘起（要解决的两个观察）

1. 模型开工前不问清目标，大量工作建立在猜测用户意图之上 → 偏差；
2. 模型排计划/执行天然串行，从不主动识别并行机会 → 慢、错过解。

## 1. 目标（字典序：唯一硬指标在前）

- **硬目标（唯一）**：POC 验证成立——"立项书 + 并行计划评审 + 复盘分类"三件交付物被**真实使用**，
  且至少在一个真实任务（run 10 校场战役）上跑通，行为指标可测改善。
- **范围（用户 2026-09-11 裁定）**：**先针对 CTF 任务**；有其他任务再泛化。
- 次要 1：验证成本（时间）最小；次要 2：花费最小。
- **非目标**（明确不做）：不写新代码/插件（POC 用文档 + SKILL）；不改动神策现有四项目形态；不建新仓库（形式后议）。

## 2. 约束

- **硬**：托管规则合规（方法论进托管 run 时不含机制先验/题源启发，红线见 `VALIDATION/SKILL-COMPLIANCE-AUDIT.md`）；
  公开仓库不落私知/密钥/flag；不破坏神策现有组件与流程。
- **软**：复用现有机制（虎符/集思/战报/审计/清单）而非另起炉灶；文档可溯源（公开技艺/自研方法论分栏）。

## 3. 验收口径（done 定义 + 停止条件）

- **POC 成立** = 三交付物被实际使用 + 行为指标改善：
  - a. **立项书模板**：run 10 开打前有经用户审定的立项书；此后每个"项目级任务"先过立项书再开工；
  - b. **计划评审协议**：run 10 调度计划含依赖图/关键路径/并行度上限说明；主 agent 亲解 0 题（沿用 A1 标准）；
  - c. **复盘分类机制**：run 10 战后教训按四栏（预期 vs 实际 / 决策-结果对照 / 根因 / 教训分类）落账并走升格/归档。
- **停止/失败条件**：若 run 10 上三交付物形同虚设（agent 未实际引用/执行），或行为指标不升反降 → POC 失败，回到讨论。
- **时间盒**：run 10 一个战役周期（1 个 ≤6h run + 战后复盘）。

## 4. 规则域（红线前置识别 + 变更条款）

- 红线 = 第 2 节硬约束；本项目的"规则域识别"必须发生在任何实质动作之前（托管规则教训的直接应用）。
- **变更条款（用户 2026-09-11 裁定）**：目标/红线变更时，**基于当前已完成工作重新立项排计划，谋定而后动**；旧计划即时作废，不续行。

## 6.5 评审分层（托管全自动模式的适配——用户 2026-09-11 提问裁定）

托管战役是全自动的（排名按用时，run 中任何人工闸门 = 烧平台时钟），因此评审分三层：

1. **开打前（人工审定，唯一人工闸门）**：立项书在本会话完成审定（即当前这个动作）——不烧钟；
   立项书随开战令打包进 run。这是 run 启动前模型与用户的**最后一次交互窗口**，所以立项书必须
   同时承载"目标/约束/验收/规则域 + run 内判断框架"（变更条款即一例）。
2. **run 中（agent 自审 + 机制校验，零人工）**：主 agent 按计划评审协议自审（计划必须含依赖图/
   关键路径/并行度上限，缺了重写）；机制层可加自动校验（runner/watch 检查计划产物存在且结构完整，
   缺失时明确提示主 agent——"靠配置不靠纪律"）。
3. **战后（人工回审）**：复盘时人工对照"计划 vs 实际执行"（决策-结果对照表），教训分类落账，
   评审协议据此进化 → 下一 run 的主 agent 自审能力被喂得更好。

- 推论：全自动模式下立项书比人工模式**更重要**——它是 run 内所有自主判断的唯一授权来源。
