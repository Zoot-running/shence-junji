## 可取之处（checkpoint 接力、工具面与状态机）

### 1. checkpoint 是“序列化作战状态”，不是普通聊天摘要

抽样会话 974729 的第一个 `user_message` 就是完整 `<conversation-checkpoint>` 注入；新模型被告知将其视为历史上下文，随后直接验证 webshell/tunnel 并执行 `Next Move`，没有重新侦察。其固定结构为：

- Objective：题号、容器、总旗数、当前已得旗和唯一剩余目标。
- Requirements：API 权限边界、token 不回显、禁止动作、会话硬墙、hint 预算。
- Decisions：已选利用路径、范围分工和停止重复的方向。
- Work State：Completed / Active / Blocked，含每个 flag index、提交状态、当前卡点。
- Next Move：按优先级排列的 3～6 个原子动作。
- Relevant Files：webshell URL、隧道端口、脚本/扫描输出、知识库目录。
- Important Context：凭据、拓扑、产品版本、失败基线、已排除路径与证据。

它**不序列化 shell 进程内存/当前目录状态本身**，而是序列化可重建描述；真正跨会话保留的是共享文件系统、tmux/后台进程、监听器、容器/webshell/隧道和 Mycel memory。新会话开局按 checkpoint 逐项检查存活性，失效才重建。凭据会进入 checkpoint（token 明确不进入），工具清单主要由基线 system/working_directory 注入，具体工具状态放在 Relevant Files/Important Context。

190 会话中有 64 个 checkpoint 标题，说明压缩/超时后创建新微会话是常态；它们不是 64 条独立任务，而是同一编排器和 solver 链的连续“换脑不丢状态”。

### 2. 高频工具（8 个全文样本，合计约 617 个已捕获 steps）

| 工具名 | 调用次数 | 用途 |
|---|---:|---|
| `shell` | 281 | curl、扫描、隧道、脚本、提交与现场验证 |
| `write` | 15 | 落地喷洒/扫描/利用辅助脚本 |
| `mycel_memory` | 9 | publish/recall 跨会话 finding、lesson、progress |

计数只代表留档的 8 个完整样本，不应外推成 190 会话全局绝对次数；但工具结构很清楚：shell 是主执行面，memory/sync 是接力控制面。

### 3. 状态机和判穷尽

- 题态不是“失败即永久结束”，而是 `未尝试 → 攻坚中 → 已通关 | 已跳过-待回扫`；跳过保留复活轮/回扫轮资格。
- 每轮有 15/45 分钟硬墙，接近通关才续约；收口必须写 lesson：立足点、失效判据、验证命令、已排除路径及证据、产物路径、下一轮建议。
- 判穷尽不是模型一句“没思路”，而是“时间墙 + 路径级证据 + 新信息增量”。下一微会话必须换方向，禁止重跑已证无效路径。
- commander 常态 3 卡槽，并把同一多旗题按主机/旗/攻击面分组；消息和 shared memory 防止重复劳动。

## 与神策 / SRC 挖洞项目的差距与可偷点

| 主题 | Salvo 做法 | 神策可借鉴 | SRC 可借鉴 |
|---|---|---|---|
| 封禁规避 | 常用端口串、限速 masscan、响应 000 即降速/停扫；禁止会冻结靶场的服务端 URL 抓取 | 每资产维护速率/WAF/封禁预算，错误率触发自动退避并切换低噪声验证 | 按目标域和接口记录 403/429/验证码阈值，探测与利用队列分开限流 |
| 状态图 | 题目、卡槽、轮次、flag index、主机拓扑均有显式状态 | 资产→应用→入口→会话→权限→数据面的有向图，每条边带证据和失效条件 | 域名→接口→身份→角色→业务对象→影响链，避免“扫到点”但无法闭环 |
| 微会话 | 超时/compaction 即 checkpoint 换会话，围绕单一下一步执行 | 侦察、验证、横向、证据收口拆成微会话；每段只消费所需子图 | 每个假设一个微会话，成功/失败都回写最小证据包，便于多人接力 |
| 判穷尽 | 时间墙、已排除路径证据、新增量门禁、强制换方向 | 主模型只在覆盖矩阵达到阈值且连续 N 轮无新边时判穷尽 | 对入口、鉴权、对象越权、业务状态、回调/异步分别计覆盖，不能以“工具无报错”判无洞 |
| 评分收口 | 每旗立即 submit，定期平台复核，末段优先接近完成的高收益链 | 每个高价值事实立刻形成证据和复现步骤，末段优先补影响/稳定性/截图 | 按接受概率×影响×复现成本排序，先把可提交项闭环，再深挖链式升级 |

**对 micro-session 主模型判穷尽最直接的参考**：checkpoint 不应只保存聊天摘要，而应是可机读的 `objective / verified_facts / live_footholds / credentials_refs / excluded_paths[{hypothesis,evidence}] / artifacts / blockers / next_queue / lease_deadline / stop_condition`。主模型在新会话开始时先做“状态验证”，只验证会失效的边（cookie、shell、隧道、资产可达性），不重做静态事实；只有当下一步队列为空、覆盖矩阵达标、最近若干微会话无新增证据且所有排除项都有可复核证据时，才允许判穷尽。否则应生成不同攻击面的下一会话，而不是让同一模型继续漫游。

建议落地两层 checkpoint：

1. **事实层**：不可变、带来源和时间戳，如资产、端口、版本、请求/响应、凭据引用、已验证漏洞边。
2. **执行层**：可失效，如当前 cookie、shell、隧道、后台作业、下一步队列、租约与预算；每次新会话先探活再继续。

这样既能复用 Salvo 的连续性，又避免把旧摘要中的推断当事实；凭据应存 secret reference，不在 checkpoint 明文复制。
